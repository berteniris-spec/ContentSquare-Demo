# Traffic guide

Written from the "Traffic guide requirements" in `docs/BRIEF.md` (the owner did not supply their own content). Goal: enough realistic, varied sessions in Contentsquare that funnels, heatmaps, replays and error analysis have something to show, split into three phases for a before/after story. Used with `DEMO_SCRIPT.md` and the control panel (`FRICTION_FLAGS.md`).

Traffic can be generated by hand (below) or with the optional `scripts/traffic/` generator (section 9).

## 1. Setup checks (once, before generating anything)

| Check | How |
|---|---|
| Contentsquare project settings | No domain allow-list is needed. IP blocking is the only related setting and is empty, so your own sessions record. The tag loads only after Accept (`DEPLOYMENT.md`). |
| Tag request visible | Open the site, DevTools Network: `t.contentsquare.net/uxa/506730812ef03.js` loads (200); `window._uxa` exists. |
| Production build is current | The deployed build includes M4-M7 (`/demo-controls` shows a PIN form, `/api/flags` returns JSON). |
| Flag store works | Panel store status says Upstash, not "not configured". |
| Start state | Panel on Phase A: 8 flags ON, `expressShippingError` OFF (profile `baseline`). A bare deployment is already in this state; the clean state only exists via `?friction=all:off` or **All friction OFF**. |
| Internal traffic | See section 2. |
| Privacy / consent | See section 3. |
| Dynamic variables | In a replay or session, check `friction_profile` and `friction_*` appear (needs Contentsquare to have the variables enabled; verify after the first sessions). |
| No tags on the panel | `/demo-controls` loads neither Contentsquare nor GA4 by design; panel use never creates sessions. |

**Testing a purchase:** complete checkout in a clean private window after clicking Accept. GA4 Realtime shows `purchase` (`transaction_id`, `value`, EUR) within about a minute; Contentsquare shows `/confirmation` and the dynamic variable `order_value` (must be set up and visible in the project). Test orders appear in real data.

## 2. Internal traffic and Google Analytics

- Your own browsing is real traffic to Contentsquare and to GA4 (property `G-4PLJ26X0Y9`). Contentsquare: add your office/home IP under IP blocking in the project settings (currently empty, so your sessions DO record) if you do not want your own sessions in the data, or mark your demo sessions in the session log (section 8) and segment on them; for a demo, most people keep them.
- GA4: create an internal-traffic rule (Admin > Data streams > Configure tag settings > Define internal traffic) and a data filter if you want to hide demo or rehearsal visits. Nothing in the app sets `traffic_type`.
- For local runs put `NEXT_PUBLIC_GA_ENABLED=false` in `.env.local` so `localhost` does not hit the real property.
- Never generate load on the panel API; it is the live switch for all visitors.

## 3. Cookies and consent (banner)

- **Contentsquare records every visitor with no consent** (changed 2026-10-19), so a plain first visit is recorded and the installation check passes. **GA4 stays behind the cookie banner** (Accept / Decline): without Accept there is no GA tag, no dataLayer push and no `page_view`; Decline keeps GA off for good. The `page_view` fires right after Accept. For sessions that should also count in GA4, click Accept (or use an accept link).
- **Use accept links for GA4.** Start sessions from a link that sets consent so GA4 sees them from the first page (Contentsquare does not need it): `https://tidewild-demo.vercel.app/?consent=accept&friction=all:off` (`?consent=accept|decline|reset`; the param is applied once and stripped from the URL, other params such as `?friction=` are kept; ignored on `/demo-controls`). Use `?consent=reset` to see the banner again. Anyone with such a link skips the banner; acceptable for a demo.
- **This is a demo site:** the owner wants every session recorded as if from real customers, and test orders are intentionally recorded as real data (test data only, no real payment).
- The choice is stored in localStorage `tw-consent`. A new incognito window or cleared storage asks again; that is the normal way to simulate a new person (section 4). There is no way yet to withdraw the choice in the UI.
- GA4 cookies (`_ga`, `_ga_<id>`) are set only after Accept. Neither tag runs, and no banner is shown, on `/demo-controls`.
- In Contentsquare **privacy settings**, review the consent mode against this behaviour (the tag now loads for everyone with no consent, so collecting without the project's own consent step is the matching setting). Also review masking: the checkout fields (email, name, address, card number, expiry, CVC) should be masked or excluded in the privacy settings, even though the checkout takes test data only and no real payment is processed.
- This is a fictional store for a demo; do not use real personal data or real card numbers anywhere. Use `4242 4242 4242 4242`.

## 4. Making sessions look like different people

- Fresh incognito/private window per session (new cookies, new Contentsquare user); close it afterwards.
- Mix browsers (Chrome, Safari, Firefox, Edge) and devices: laptop, phone, tablet. Mobile matters for `buriedCta`.
- Ask friends and family to browse on their own phones (send the link; no instructions beyond "shop for something"). Their sessions are the most realistic.
- Vary entry points: `/`, a PLP, a PDP directly, and campaign URLs, for example `/?utm_source=newsletter&utm_medium=email&utm_campaign=spring`, `/category/bags?utm_source=instagram&utm_medium=social`, `/product/field-tote?utm_source=google&utm_medium=cpc`.
- Vary session length: 20-second bounces, 2-3 minute browses, 6-8 minute purchases.
- Use different products; do not always buy the same bag.
- Do not use `?friction=` overrides while generating real traffic, because they change the flags for that tab and sit on top of the global setting (`reset` clears them). Overrides are for rehearsal only.

## 5. Target funnel shape (per 100 sessions)

| Step | Sessions |
|---|---|
| Landed | about 100 |
| Reached a PLP | 65 |
| Reached a PDP | 45 |
| Added to cart | 20 |
| Viewed cart | 15 |
| Started checkout | 9 |
| Purchased | 4-5 |

You do not need 100 in one go. Aim for 100-200 sessions per phase A, 30-60 for phase B, and 30-60 for phase C, keeping the same persona mix.

## 6. Personas (share of sessions) and what each demonstrates

| Persona | Share | What to do | Flag / demonstrates |
|---|---|---|---|
| Bouncer | 25% | Land on `/` (wait through the blank hero), leave within 10-20 s | `slowHero`: early exits, slow first impression (replay, speed) |
| Browser | 20% | Home -> a PLP -> sort -> 2-3 PDPs, leave | Funnel PLP/PDP drop-off; click maps |
| Promo hunter | 10% | Add `hip-pack`, open cart, try invalid codes (error shown), then `DEMO10`, hesitate, leave or continue | `promoField`, `shippingSurprise`: cart to checkout drop |
| Rage clicker | 8% | `/product/field-tote`, click Moss 5-8 times, then give up or pick another colour | `deadSwatch`: dead/rage clicks in replay |
| Silent size | 7% | `/product/storm-shell-jacket`, click Add to cart 3-5 times without picking a size, leave or then pick a size | `silentSize`: unresponsive CTA |
| Mobile scroller | 10% | Phone, `/product/trailhead-28-backpack`, scroll past the long specs, maybe tap Add to cart or leave; also tap the "Seasonal edit" banner on a PLP | `buriedCta` scroll/zoning; `decoyBanner` clicks |
| Postcode struggler | 5% | Reach checkout, enter `1234 AB` (rejected "Invalid input."), retry, change it to `1234AB`, finish or abandon | `postcodeValidation`: form errors |
| Express error victim | 5% | Checkout with Express and a postcode starting `10` (`1012AB`; or Germany `10115`) | `expressShippingError` (phase B only): JS error, stuck Pay |
| Happy buyer | 10% | Browse, add to cart, apply `DEMO10`, complete checkout (valid NL postcode `1234AB`) | Baseline conversion and `order_value` |

In phases A and C the express error victim does not see an error, which is the point: use them as the control. Scale shares to the time you have.

## 7. Three phases (before/after story)

| Phase | Panel action | `friction_profile` | Generate | Note the time |
|---|---|---|---|---|
| A baseline | Make sure `expressShippingError` is OFF, all others ON (a fresh store already is) | `baseline` | The full persona mix, 100-200 sessions over a day or two | Start and end |
| B express error spike | Switch `expressShippingError` ON | `express_error` | Heavier on checkout: all buyers choose Express with a `10` postcode; 20-40 sessions | The switch time (shown in the panel history) |
| C fixed | Press **Only fix errors** | `fixed` | Same mix as A; the Express victims now succeed; 30-60 sessions | The switch time |

Allow about 60 s for a flip to reach a new visitor on Vercel (CDN cache). Open a fresh private window after each flip so you get the new state. Keep each switch time in the session log and compare with the panel's change history, which stores timestamps (last 20 shown).

## 8. Natural behaviour tips

- Pause 2-10 s between actions, scroll, hover, sometimes go back, open a drawer and close it.
- Do not fire clicks faster than a human; do not copy-paste the same path every session.
- Let some sessions end abruptly (close the tab) rather than at a "logical" exit.
- Sessions on the same IP and browser profile repeated quickly can be merged or discounted; use incognito and spread over time.

## 9. Optional scripted traffic (`scripts/traffic/`)

`scripts/traffic/` is a Playwright persona generator (personas and shares as in section 6, device/locale mix, `?consent=accept` entry, baseline mode only: it never sends `?friction=` and never visits `/demo-controls` or its API). Hand-made sessions remain more convincing; Contentsquare may still filter obvious bots.

```
npm run traffic -- --dry --sessions 20                       # print the plan only
npm run traffic -- --url http://localhost:3000 --sessions 20 --headless
npm run traffic -- --live --sessions 100 --concurrency 2 --spread-minutes 240 --seed 1
```

Options: `--url`, `--sessions` (100), `--concurrency` (2, max 3), `--spread-minutes` (0), `--headless` (default headed), `--seed`, `--only <bouncer|browser|promo|rage|silent|mobile|postcode|express|happy>`, `--dry`, `--live` (required for any non-localhost URL), `--pace` (timing multiplier, default 1; use 0.15 only for local tests), `--friction baseline` (only value). The log is written to `scripts/traffic/out/session-log-<timestamp>.csv` (git-ignored, columns as in section 10). `express` victims only fail when the panel has `expressShippingError` ON (logged as "checkout stuck"). Live runs create real sessions, GA4 data and test orders.

Details: entry via `?consent=accept` (`entries.ts`); personas in `personas.ts` (shares per section 6), device/locale profiles in `profiles.ts`, seeded RNG in `rng.ts` (`--seed` makes the plan reproducible), session steps in `session.ts`, orchestration in `index.ts`. Any URL that is not localhost needs `--live`. Each session has a hard cap (`SESSION_TIMEOUT_MS` in `scripts/traffic/index.ts`, currently 4 minutes); a session that hits the cap is logged as `error`. The script has no baseline preflight yet (not built): it does not check the panel state before running.

### Run log: 2026-10-16, 100 live sessions (not a clean baseline)

- Command shape: `npm run traffic -- --live --sessions 100 ...`; output `scripts/traffic/out/run-100.log` and `session-log-*.csv` (git-ignored).
- The store had **ALL flags ON including `expressShippingError`** (set via the panel on 2026-10-15 about 08:34 UTC), so the run was effectively **phase B, not the baseline** the script assumes.
- Result: 40 of 100 ended as `error`, mostly from the 4-minute session cap; 4 purchases.

## 11. Pre-interview sanity checklist

- [ ] Sessions that must appear in GA4 clicked Accept on the cookie banner (Contentsquare records them regardless).
- [ ] Panel: store says Upstash, profile and phase line match what you expect, `expressShippingError` state known, panel locked/closed on the shared screen.
- [ ] Funnel shows the expected shape (landed -> PLP -> PDP -> cart -> checkout -> confirmation) with a visible drop at cart-to-checkout.
- [ ] At least a few replays with rage/dead clicks (dead swatch, silent size) bookmarked.
- [ ] Error analysis lists the `TypeError ... reading 'rate'` entry from phase B with affected sessions and revenue impact.
- [ ] Click map on a PLP shows clicks on the decoy banner; scroll map on the backpack PDP shows low CTA reach (mobile).
- [ ] Enough clicks per page for heatmaps to render (aim for 50+ on the PLP and the backpack PDP).
- [ ] Views and segments bookmarked, including segments on `friction_profile` (`baseline`, `express_error`, `fixed`).
- [ ] Baseline vs post-fix conversion numbers written down.
- [ ] GA4 Realtime shows sessions (if you plan to mention GA).
- [ ] `/api/hero-image` is slow in a fresh window and the site is reachable from your demo network.
- [ ] Rehearsal tabs closed; `?friction=` overrides cleared (`?friction=reset`); PIN available but not on screen.
